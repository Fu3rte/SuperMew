# RagProof PRD（纯需求）

> 文档版本：v0.1（2026-09-09）
> 状态：需求草案
> 范围：产品需求，不含技术选型与实现设计
> 参考基线：开源项目 SuperMew（MIT）作为功能对标基线，本 PRD 描述"要做成什么"，不描述"用什么做"
> 项目名：RagProof（知鉴）——企业 RAG 质量治理平台

---

## 1. 背景与问题

企业把 RAG 知识库问答上线后，团队会持续调整分块策略、Embedding 模型、召回数量、混合检索权重、重排开关与阈值、回答/评判模型，以及重建索引。当前缺少一套"改动是否真的变好、能不能发布"的度量与管控手段，导致：

| 问题 | 现状表现 |
| --- | --- |
| 调参靠人肉 | 改一个参数，手工问三五条问题，凭感觉判断 |
| 结论不可复现 | 没有固定测试集，换人再测结论对不上 |
| 假对比 | 换模型/索引后拿旧结论比，误判"变好了" |
| 上线无门禁 | 改坏了靠 code review 拍脑袋，无人拦截 |
| 出错无法归因 | 不知道是没召回、重排排掉了，还是证据不足硬答 |
| 评测不可信 | 用大模型当裁判分数飘；或手改数据美化指标 |
| 事故无证可查 | 拿不出当时用的配置、索引、数据与指标记录 |

**一句话需求**：企业 RAG 上线前后，如何证明"这次改动是真变好"，并且不让变差的版本发出去。

## 2. 目标用户与角色

| 角色 | 关注点 | 主要动作 |
| --- | --- | --- |
| RAG / AI 应用工程师 | 我的改动有没有让质量变好 | 维护标注集、跑评测、看报告、调参 |
| 评测 / QA | 评测结果是否可信、可复现 | 维护指标口径与门禁阈值、复核报告 |
| 发布负责人 | 这个版本能不能发 | 看门禁结论、审批发布 |
| 运维 / 值班 | 出问题怎么定位 | 查历史报告、复盘回退 |
| 管理员 | 谁能用、配置怎么管 | 管理模型配置、数据集、权限 |

## 3. 核心场景

**S1 上线前验收**
工程师改了重排阈值 → 提交变更 → 系统按版本化数据集真实执行 RAG → 产出指标与门禁结论 → 未达标则拦截发布并给出回退 case 列表。

**S2 调参对比**
工程师想比较两套检索配置 → 系统分别执行 → 以同一基线对比指标 → 输出差异报告（哪项变好、哪项回退）。

**S3 歧义澄清**
用户提问含糊 → 系统识别歧义并请求补充信息 → 用户澄清后继续回答 → 全程可追溯，不硬答幻觉。

**S4 事故复盘**
线上回答错误 → 值班按时间找到当时报告 → 报告绑定语料、索引、配置、模型与源码身份 → 定位是数据问题还是配置问题。

**S5 持续评测（V1）**
语料或索引更新 → 自动触发重测 → 指标漂移超阈值告警。

**S6 多角色协作问答（V2，非 MVP）**
复杂问题 → 系统规划为多步任务，由不同职责的执行单元分工完成检索、对比、核验、撰写 → 汇总为带证据的答案，并有预算与失败恢复约束。

## 4. 产品目标与非目标

**目标**
- 让每次 RAG 改动都有可复现、可对比、可审计的质量结论。
- 让"能不能发布"从人判断变成规则判定。
- 让评测结果本身可信：数据版本化、来源可追溯、大模型不当唯一判官。

**非目标（本期不做）**
- 不做通用 Agent 开发框架。
- 不做向量数据库、Embedding 模型本身。
- 不做多租户 SaaS 商业化与计费。
- 不做生产级高可用与大规模并发（单机 / 小团队部署口径）。

## 5. 功能需求

> 优先级：P0 = MVP 必须；P1 = V1；P2 = V2。

### FR-1 知识库与文档管理（P0）
- 支持上传多格式文档，完成解析、分块、入库。
- 文档版本不可变；问答只使用"当前已发布版本"。
- 支持查看文档处理状态与失败原因。

**验收**
- 上传文档后能看到解析/分块结果与状态。
- 修改文档产生新版本，历史版本可查；问答不受未发布版本影响。

### FR-2 RAG 问答与证据溯源（P0）
- 回答问题必须给出引用来源（文档/片段）。
- 检索不到证据时应明确"信息不足"而不是编造。
- 答案需可展开查看检索、评判、重写等中间过程。

**验收**
- 每个回答都能追到具体证据片段。
- 无证据问题的回答为明确弃答，且被记录。

### FR-3 歧义澄清（HITL）（P0）
- 识别歧义或信息不足时，暂停并请求用户补充。
- 用户补充后从暂停点继续，不重头再来。
- 澄清记录进入评测与审计。

**验收**
- 澄清后同一会话可继续，过程可追溯。
- 重复提交澄清不会产生重复任务或重复计费。

### FR-4 评测数据集管理（P0）
- 支持导入/维护版本化评测数据集（问题、期望行为、标注证据、参考答案、标签）。
- 数据集任何改动都产生新版本，旧版本的评测结果不可直接复用。
- 支持按标签分类（单事实、跨文档、多跳、对比、时间/版本、表格、代码、歧义、无知识、冲突、注入等）。

**验收**
- 修改数据集后，旧结果被系统拒绝复用。
- 能按标签筛选与统计。

### FR-5 评测执行（P0）
- 支持两种评测来源并明确区分：
  - 离线契约评测：不依赖真实模型/索引，用于验证评测规则本身可复现。
  - 真实评测：连接真实模型与索引执行。
- 评测以"任务"形式执行，支持进度查看、取消、失败重试。
- 每个用例的执行结果（检索证据、答案、评判原因）持久化。

**验收**
- 离线评测无需模型即可跑通。
- 评测任务可取消；执行者失联后任务状态能收敛，结果不被过期执行者覆盖。

### FR-6 指标与门禁（P0）
- 系统需计算并展示检索、回答、澄清、成本等指标（见第 6 节）。
- 支持配置门禁策略：
  - 关键用例零回归。
  - 逐指标阈值。
  - 逐指标允许的最大回退幅度。
  - 评测来源校验（离线结果不得冒充真实结果）。
- 门禁判定输出通过/失败，并给出失败原因。

**验收**
- 指标回退超过阈值时，门禁判定为失败。
- 离线结果与真实结果不能混用比较。

### FR-7 评测报告与追溯（P0）
- 每次评测产出可导出的报告（结构化 + 可读两种形式）。
- 报告必须绑定评测时的：数据集版本、语料版本、索引身份、模型与检索配置、评测规则版本。
- 报告不得包含密钥、原始异常等敏感信息。

**验收**
- 用不同配置/索引产生的报告不能被当作同一来源直接对比。
- 报告可离线查看，能定位到具体回退用例。

### FR-8 发布门禁与流水线集成（P0）
- 提供命令行/接口形式的门禁入口，可接入持续集成。
- 门禁失败时返回非零结果并输出失败详情。
- 支持与基线（上一版本/主干）对比。

**验收**
- 人为制造一次指标回退，流水线能被卡住并输出原因。

### FR-9 失败归因与趋势（P1）
- 按失败类型聚合：超时、指标不达标、调用失败、缺证等。
- 输出失败 Top-N 与趋势视图，支持按版本/配置对比。

**验收**
- 报告能回答"这批失败主要是什么原因"。

### FR-10 Holdout 与开发集对比（P1）
- 支持将评测集划分为开发集与 Holdout 集。
- 发布前用 Holdout 复验，防止过拟合开发集。
- 输出两组指标对比。

**验收**
- 能导出一份"开发集 vs Holdout"的对比报告。

### FR-11 持续评测（P1）
- 语料或索引更新后自动触发重测。
- 指标漂移超过阈值时告警。

**验收**
- 更新语料后无需人工触发即可得到新报告与告警。

### FR-12 多步骤专业 Agent 协作（P2，非 MVP）
- 复杂问题可规划为带依赖的多步任务，由不同职责单元分工完成。
- 每个步骤有明确预算（时间/调用次数）与失败恢复策略。
- 步骤级过程可观测、可追溯；预算超限时整体熔断。
- 新路径必须纳入评测数据集与门禁，证明不产生回退。

**验收**
- 复杂问题走多步路径，简单问题不被拖入。
- 单步失败可重试或降级，不影响最终可解释性。
- 新路径有对应评测用例与门禁指标。

### FR-13 权限与团队协作（P1，可选）
- 支持角色区分：管理员、评测维护者、普通使用者。
- 数据集、模型配置、门禁策略的修改有权限控制与操作记录。

**验收**
- 非授权用户无法修改门禁策略与数据集。

## 6. 指标口径（业务定义）

| 类别 | 指标 | 定义 |
| --- | --- | --- |
| 检索 | Recall@k | 前 k 条检索结果命中标注证据的比例 |
| 检索 | Document Recall@k | 前 k 条结果命中标注文档的比例 |
| 检索 | MRR@k | 首个命中证据排名的倒数均值 |
| 检索 | NDCG@k | 检索排序质量 |
| 检索 | Gold Chunk Coverage | 标注证据块被召回的比例 |
| 回答 | Case Pass Rate | 通过验收的用例比例 |
| 回答 | Outcome Accuracy | 回答/弃答/澄清判定正确率 |
| 回答 | Route Accuracy | 路由判定正确率 |
| 回答 | Complexity Accuracy | 复杂度判定正确率 |
| 回答 | Groundedness / Unsupported Claim Rate | 有证据支撑度 / 无支撑断言比例 |
| 回答 | Conflict Disclosure Rate | 正确披露证据冲突的比例 |
| 澄清 | HITL Accuracy / Resolution Success | 澄清命中率 / 澄清后成功解决比例 |
| 稳定性 | Provider Failure Rate | 调用失败比例 |
| 成本 | Cost per Answer / Latency | 单次回答成本与时延 |

> 指标必须由确定性规则计算；大模型只能用于语义维度的辅助评判，且必须可被离线断言覆盖。

## 7. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 可复现 | 同一数据集 + 同一配置 + 同一语料，评测结果可重复；任何输入变化都会使旧基线失效 |
| 可审计 | 评测报告、配置变更、数据集变更、发布判定都有记录 |
| 可信 | 评测来源可区分；不允许静态/离线结果冒充真实质量结果 |
| 成本可控 | 评测有预算上限（用例数、时长、调用次数），超限熔断 |
| 安全 | 报告与日志不落密钥、原文敏感内容与原始异常 |
| 部署 | 支持单机 / 小团队部署，离线评测不依赖外部模型即可运行 |
| 性能 | 单次评测任务可取消；执行者异常时任务状态能收敛 |
| 可观测 | 问答与评测链路的关键步骤可查看（检索、评判、重写、路由） |

## 8. 版本范围

| 版本 | 范围 | 目标 |
| --- | --- | --- |
| MVP | FR-1 ~ FR-8 | 跑通"数据集 → 评测 → 门禁 → 报告 → 流水线卡口"闭环 |
| V1 | + FR-9、FR-10、FR-11、FR-13 | 从"能评测"升级为"持续治理 + 团队可用" |
| V2 | + FR-12 | 从"单轮 RAG"升级为"多步骤专业 Agent 协作"，并纳入门禁 |

## 9. 成功指标

- 一次配置变更从"人工试错半天"缩短为"自动评测 + 门禁判定，30 分钟内出结论"。
- 上线前 100% 经过门禁判定，指标回退可被拦截。
- 任一历史报告可在 5 分钟内定位到当时的配置、数据与回退用例。
- 离线评测零外部依赖即可复现门禁结论。

## 10. 风险与开放问题

| 风险 | 说明 | 应对方向 |
| --- | --- | --- |
| 标注集质量 | 数据集太小或标注不准，门禁结论无意义 | 先保证核心场景覆盖，逐步扩充到 200 条 |
| 评测成本 | 真实评测消耗模型调用 | 预算上限 + 离线评测优先 + Holdout 抽样 |
| 大模型判分不稳定 | 语义指标波动 | 关键指标确定性化，LLM 仅辅助且可断言 |
| 多步骤改造风险 | 改状态模型可能破坏可复现性 | 后置到 V2，先扩评测再上协作 |
| 与参考基线混淆 | 基于开源项目二次开发 | 明确"参考并改造"，自研增量单独记录 |

## 11. 术语

- **评测用例（Case）**：一条带期望行为与标注证据的评测样本。
- **数据集版本（Dataset）**：一组评测用例的不可变快照。
- **观测（Observation）**：某次真实/离线执行产生的检索与回答记录。
- **基线（Baseline）**：用于对比的上一版评测报告。
- **门禁（Gate）**：判定评测是否通过发布要求的规则集合。
- **来源（Provenance）**：评测结果产生方式（离线契约 / 真实执行）的标识。
