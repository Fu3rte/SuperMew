## 1. 一句话理解这个项目

**SuperMew 是一个"知识库优先"的 Agent 平台**：用户上传文档构建知识库，然后提问，平台用 RAG 检索证据、生成回答、并在证据不足时明确弃答或反问。

**但它真正的差异点不在"能问答"，而在"问答质量可证明、可管控、可发布"**：

> 改了一行检索配置，跑版本化数据集，算出 `document_recall_at_10` 从 0.92 掉到 0.81，超过允许回退幅度 0.02，**门禁直接判 FAILED、卡住 Pull Request，并在报告里点名是哪几条 case 回退了**。

普通 RAG 项目解决"能不能答"，这个项目解决"**敢不敢上线**"。

**RagProof（知鉴）** 是 `prj-pre/开发计划.md` 里给"基于 SuperMew 二次开发"这件事起的项目名。当前仓库本体仍叫 SuperMew（README 标题为 `SuperMew 项目说明`）。

```
仓库现状（git remote）：
  origin   → https://github.com/Fu3rte/SuperMew.git      （你的 fork）
  upstream → https://github.com/icey1287/SuperMew.git    （原始上游）
```

**贡献清单的判定方式**就是 `git diff upstream/main`。

## 2. 业务背景：谁在用、为什么痛

### 2.1 目标用户

**不是 C 端消费者**，而是企业里做 RAG 应用的 AI 团队：RAG 工程师、技术 lead、值班运维。

### 2.2 他们每天在改什么

chunk 大小与切分策略、embedding 模型、`top_k`、混合检索权重、rerank 是否开启与阈值、Answer/Grader/Evaluator 各用哪个模型、是否重建索引。

这些都是**高频、低风险感知、但会真实改变质量**的参数。

### 2.3 七个痛点

| 痛点 | 现状（没有这个平台时） |
| --- | --- |
| 调参靠人肉 | 改一个参数，手工问三五条问题，凭感觉判断"好像好点了" |
| 结论不可复现 | 没有固定测试集，换个人再测结论对不上 |
| 假对比 | 换了模型/索引后拿旧结论比，得出"变好了"的错觉 |
| 上线没门禁 | 改坏了靠 code review 拍脑袋，没人拦 |
| 出错无法归因 | 答错了不知道是没召回、重排排掉了，还是证据不足硬答 |
| 评测本身不可信 | LLM 当裁判分数飘；或有人手改数据美化指标 |
| 出事无证可查 | 拿不出"当时用哪套配置、哪个索引、哪份数据、什么指标" |

### 2.4 一个真实场景（本项目的核心叙事）

把 rerank 阈值调高一点，手工测 5 条感觉更好就上线。结果多跳问题变差，但单事实问答没受影响 —— **人肉测试根本发现不了**。

本项目的做法：跑版本化数据集 → 真实执行 RAG → 算确定性指标 → 发现 `document_recall_at_10` 从 0.92 掉到 0.81、超过 `max_regression: 0.02` → 门禁 FAILED、卡住 PR、报告点名回退的 case。

### 2.5 与"普通 RAG 项目"的区别

| 维度 | 普通 RAG 项目 | 本项目 |
| --- | --- | --- |
| 解决什么 | 能问答 | 问答质量**可证明、可管控、可发布** |
| 调参方式 | 人肉试 | 数据集 + baseline + 门禁 |
| 结果可信度 | 看感觉 | provenance + 指纹 + 确定性指标 |
| 上线 | 拍脑袋 | CI 卡口 |
| 出问题 | 说不清 | 报告可追溯 + case 级定位 |

## 3. 领域概念词典（核心对象）

以下是 `CONTEXT.md` 定义的正式术语。**这些名字不能混用**，混用会导致沟通与代码双重歧义。

### 3.1 会话与执行

| 术语 | 定义 | 禁止叫法 |
| --- | --- | --- |
| **Thread** | 用户拥有的连续对话容器，服务端生成安全 ID（`thread_<uuid>`）。按 sequence 保存 Message，用只随 append 递增的 version 保护并发写入。自身 lifecycle status 与活跃 Run status 是**两个独立事实**。 | Session、conversation session |
| **Message** | Thread 中不可变排序位置上的用户或 assistant 记录。assistant Message 可从 streaming 过渡到 completed / failed / cancelled / incomplete。 | Chat item、bubble |
| **Run** | 一次绑定用户、Tenant、Thread 与幂等键的**持久化** Agent 执行。一个 Run 恰好拥有一个用户 Message 和一个 assistant Message。 | Request、task、chat request |
| **Event** | 属于单个 Run 的版本化、单调 sequence 事实。**SSE 是 Event Journal 的可恢复投影，不是事实来源**。 | SSE chunk、stream message |
| **Checkpoint** | Run 在可恢复图节点上的持久状态，与 Run、Thread、用户和一次性 HITL token 绑定。 | Pending state、resume cache |
| **HITL** | Human-in-the-loop 暂停状态。Run 进入 `waiting_input` 后，用户回答**恢复同一 Checkpoint、同一 Run、同一 assistant Message**。 | Follow-up chat、重新提问 |

> **关键不变式**：关闭 SSE 或关闭浏览器 ≠ 取消 Run。终态只能由持久事务写入 `message.completed` 与权威 terminal Event。

### 3.2 知识与证据

| 术语 | 定义 | 禁止叫法 |
| --- | --- | --- |
| **Knowledge Base** | 可按 Tenant 与权限范围检索的一组 Document。 | Collection、folder |
| **Document** | 知识目录中的稳定逻辑身份，指向当前已发布的 Document Version。 | Filename、uploaded file |
| **Document Version** | 一个 Document 的**不可变内容版本**。解析、切分、嵌入与索引完成后才可原子发布为当前版本。 | Replacement file、latest upload |
| **Index Job** | 负责 Document Version 解析、索引、发布或清理的持久化 worker 工作项。 | Run、BackgroundTask |
| **Evidence** | 带 Document Version、chunk、来源和内容哈希身份的**可引用检索材料**。 | Context text、raw chunk |
| **RAG Trace** | Run 对检索路线、候选、评分、降级、Evidence 与耗时的可审计投影。**不包含模型私有推理**。 | Chain of thought、debug dump |

### 3.3 模型与评测

| 术语 | 定义 |
| --- | --- |
| **Model Profile** | 持久化、**无 Secret** 的 OpenAI-compatible 模型配置（模型标识、Base URL、超时、能力声明）。API Key 不属于该身份。 |
| **Model Assignment** | 控制面中从 Answer / Fast / Grader / Evaluator **四个角色**到已启用 Model Profile 的当前映射。修改只影响之后创建的 Run 与 Job。 |
| **Model Snapshot** | Run 或 RAG Evaluation Job **创建时冻结**的完整无 Secret 模型目录。在恢复、重试和 HITL 期间保持不变。 |
| **RAG Evaluation Dataset** | 带 schema version、唯一 Case identity、人工期望与**内容 fingerprint** 的评估事实集合。 |
| **RAG Evaluation Job** | 绑定 Dataset fingerprint、GatePolicy、可选 baseline 与 Model Snapshot 的**持久化**自动评估工作项。**不是 Run**。 |

**四个模型角色**（这个拆分很关键）：

| 角色 | 干什么 |
| --- | --- |
| **Answer** | 只根据最终 Evidence 生成回答 |
| **Fast** | 快速任务：复杂度判定（simple/complex）、重写方法选择（Step-back / HyDE） |
| **Grader** | 证据评判：一次输出相关性、可回答性、歧义、置信度与 route |
| **Evaluator** | 评测时当裁判（LLM-as-judge），输出结构化分数 |

### 3.4 身份与入口安全

| 术语 | 定义 |
| --- | --- |
| **Access Token** | 短期签名 Bearer credential，带 `iat`/`jti`。正式浏览器**只在内存中持有**，页面恢复时通过 Refresh Token 重新签发。 |
| **Refresh Token** | 仅由 `Path=/auth`、HttpOnly Cookie 承载的高熵 opaque credential。服务端只存 SHA-256 hash，配合 rotation、replay detection 与撤销 ledger。 |
| **Rate Limit Decision** | 对稳定 policy 与 HMAC identity 原子消费后的 allowed/remaining/reset 结果。**不携带原始 IP、username、Bearer 或 Cookie**。 |

> **不变式**：Access Token 不落 localStorage；Redis 限流不可用时**必须 fail-closed**，不能降级放行昂贵认证路径。

### 3.5 扩展与安全

| 术语 | 定义 |
| --- | --- |
| **Skill** | 按需激活、带版本且声明允许 Tool 的领域能力包。 |
| **Tool** | 由 Registry descriptor 定义输入、输出、角色、网络、审批和预算约束的可执行能力。 |
| **Guardrail Decision** | 针对一次具体 Tool 调用的确定性 `ALLOW` / `DENY` / `REQUIRE_APPROVAL` 结果。**不是模型判断**。 |
| **Sandbox Execution** | 已通过 Guardrail 的隔离代码执行：固定 digest image、无网络、无宿主挂载、有界资源。**不替代 Guardrail Decision**。 |
| **Tenant** | 数据、Tool policy 与运行身份的最高隔离范围。 |

### 3.6 对象关系（来自 `CONTEXT.md`）

```
Thread ── 多个有序 Message + 多个串行/排队 Run
Run ── 多个 Event + 最多一个当前 Checkpoint + 投影到一个 assistant Message
Document ── 多个 Document Version，但任一时刻最多发布一个当前版本
Model Assignment ── 一个角色 → 零或一个 Model Profile
                  新 Run 创建时把所有当前 Assignment 冻结成同一个 Model Snapshot
RAG Evaluation Job ── 只消费一个 Dataset fingerprint，冻结自己的 baseline/GatePolicy/Snapshot
Skill ── 零到多个 Tool；每次 Tool 调用都必须先产生 Guardrail Decision
```

## 4. RAG 名词解释（从零开始）

这一节假设你完全没学过 RAG。已经会的可以直接跳到第 5 节。

### 4.1 RAG 本身

**RAG = Retrieval-Augmented Generation（检索增强生成）**

大模型的训练数据里没有你的企业文档，所以直接问它会瞎编（幻觉）。RAG 的思路是：**先从你的文档里检索出相关片段，把这些片段塞进提示词，再让模型基于片段回答**。

```
用户问题
   ↓
① 检索（Retrieval）：从知识库里找出最相关的几个片段
   ↓
② 生成（Generation）：把片段当"参考资料"给模型，让它据此作答
   ↓
答案（最好还能标明依据来自哪个片段）
```

RAG 的工程质量由两半决定：**检索准不准**、**生成有没有忠实于检索结果**。本项目的指标就是分别度量这两半。

### 4.2 Chunk（分块）

文档太长，不能整篇塞进模型。要先切成小段，每段叫一个 **chunk**。

关键权衡：

- 切太大：一段里混了很多无关内容，检索命中后噪声大，模型容易被干扰。
- 切太小：语义不完整，例如"响应时间为 4 小时"被切开就丢了主语。

本项目的做法是**三级分块 L1 / L2 / L3**（见 4.9 Auto-merging）。

### 4.3 Embedding（向量化）

把一段文本映射成一个高维数字向量（例如 1024 个浮点数）。**语义相近的文本，向量距离也近**。

本项目默认用 `BAAI/bge-m3` 作为 Embedding 模型（本地推理，固定 revision）。

### 4.4 Dense Retrieval（稠密/向量检索）

把问题和所有 chunk 都变成向量，找**向量最接近**的 chunk。

- 优点：能理解语义。问"续航多久"能匹配到"电池可支撑 8 小时"。
- 缺点：对**精确字面匹配**不敏感。产品型号、错误码、专有名词容易漏。

### 4.5 Sparse Retrieval 与 BM25（稀疏检索 / 关键词检索）

基于**词频统计**的经典检索算法。BM25 是其中的标准算法：某个词在文档里出现越多、在其他文档里越少见，这个文档就越相关。

- 优点：精确匹配强，型号、代码、数字命中率高。
- 缺点：不理解同义词。问"续航"匹配不到"电池容量"。

> 本项目用的是 **Milvus 2.5+ 原生 BM25**：Collection 里定义 `FunctionType.BM25`，Milvus 自己负责分词、统计、稀疏特征生成与索引维护，客户端只提交原始文本和 Dense embedding。

### 4.6 Hybrid Search（混合检索）

**同时跑 Dense 和 Sparse 两路，再把结果融合**。这是当前业界的主流做法，因为两路各有所长、恰好互补。

### 4.7 RRF（Reciprocal Rank Fusion，倒数排名融合）

融合两路结果的具体算法。**核心思想：不看原始分数，只看排名**。

```
RRF_score(doc) = Σ  1 / (k + rank_i(doc))
                各路 i
```

（`k` 是平滑常数，通常取 60。）

为什么看排名不看分数？因为 Dense 的余弦相似度和 BM25 的分数**量纲完全不同**，直接加权没有意义。用排名就能规避这个问题。

> 这是个很好的面试点：**RRF 存在的理由就是"不同检索器的分数不可比"**。

### 4.8 Rerank（重排序）

初步召回（recall）通常捞 50~100 个候选，但只需要前 5~10 个给模型。

**Rerank 用一个更慢但更准的模型，对候选重新打分排序**。典型精度换延迟的取舍。

本项目：可选 Jina-compatible Rerank Provider；**Rerank 失败时保留已有融合排序，并把降级原因写进 `rag_trace`**（`rerank_fallback_applied`），不静默退化。

### 4.9 Auto-merging（父子块自动合并）

三级分块的结构：

```
L1 = 整节 / 大段         （最粗，语义最完整，但噪声多）
L2 = 中间段落
L3 = 最小检索单元        （最细，检索精度最高，但语义易残缺）
```

规则：**用 L3 做检索**（精度高），命中后**向上合并**——如果同一父块下的多个 L3 都被命中，就把它们的父块（L2 或 L1）整体取出给模型。

这样既保留了细粒度检索的准确率，又让模型拿到完整上下文。合并顺序是 `L3 → L2 → L1`。

### 4.10 Grader（证据评判）

检索完之后，**再问一次模型：这些证据够不够回答？**

本项目的 Grader（统一一次调用）输出：

| 输出 | 含义 |
| --- | --- |
| 相关性 | 证据与问题相关吗 |
| 可回答性 | 凭这些证据能回答吗 |
| 歧义 | 问题本身是否含糊 |
| 置信度 | 判断的把握 |
| **route** | 决定下一步走向（见 4.11） |

> 这个设计是"**用 gating 代替硬答**"——证据不够就走弃答或反问，而不是让模型硬编。

### 4.11 Route（路由）

`RagRoute` 枚举的 7 个值（定义在 `backend/evaluation/rag.py`）。**注意区分来源**——Grader 的结构化输出只允许前 5 个（`pipeline.py:108`、`:130` 的 `Literal` 约束），后 2 个是评测/运行时由降级与失败路径产出的：

| route | 含义 | 来源 |
| --- | --- | --- |
| `answer` | 证据充分，直接回答 | Grader |
| `rewrite` | 证据不足，做一次查询重写再检索 | Grader |
| `clarify` | 问题有歧义，反问用户（HITL） | Grader |
| `scope_select` | 需要用户选择检索范围（HITL） | Grader |
| `no_knowledge` | 知识库里确实没有 | Grader |
| `insufficient_evidence` | 有相关内容但不足以支撑回答 | 运行时/评测侧 |
| `provider_failed` | Provider 调用失败 | 运行时/评测侧 |

对应的 **outcome**（最终结论）：`ANSWERABLE` / `NO_KNOWLEDGE` / `INSUFFICIENT_EVIDENCE`。

> **重要不变式**：Provider 失败**不能伪装成 `NO_KNOWLEDGE`**。只有健康检索确实为空时才是无知识。

### 4.12 Query Rewrite（查询重写）

检索效果差时，换个说法再检索一次。本项目的两种方法（Fast 角色一次结构化调用**二选一**）：

| 方法 | 做法 | 注意 |
| --- | --- | --- |
| **Step-back** | 生成一个更抽象的上位问题，与原问题组合检索 | 适合问题太具体导致召回不足 |
| **HyDE** | 生成一个"假设性的答案"，用这个假答案去做检索 | **该文本只用于检索，不作为回答证据** |

流程上**只重写一次**，不无限循环：重写后必须进入回答、澄清或无知识终态。

### 4.13 HITL（Human-in-the-loop，人在回路）

问题含糊（"那个产品怎么样？"——哪个产品？）时，**停下来问用户**，而不是让模型猜。

本项目的 HITL 是真正的**挂起 + 恢复**：Run 落到 `waiting_input`，Checkpoint 持久化；用户提交一次性 `hitl_token` + 幂等键后，**从同一节点恢复**，把澄清内容拼回原问题、重跑检索。

> 反例（本项目明确禁止的做法）：把 HITL 实现成"重新发一个新问题"，那样就丢了原上下文、也无法保证幂等。

### 4.14 LLM-as-judge（用模型当裁判）

回答对不对，不能靠字符串比对（"120 千克" vs "120kg"）。做法是**用另一个模型给回答打分**。

风险：**分数会飘、不可复现、可以被操纵**。本项目的防线是：

- 裁判输出**结构化分数**（固定 schema，0~1），不是自由文本
- **核心指标由确定性代码计算**（recall/MRR/NDCG…），LLM 只负责语义类维度
- 断言 LLM 评分**绝不是唯一判据**

裁判维度（`RagJudgeMetrics`）共 7 个：

| 维度 | 含义 |
| --- | --- |
| `answer_correctness` | 回答是否正确 |
| `groundedness` | 是否有证据支撑（忠于检索结果） |
| `answer_relevance` | 是否答了所问 |
| `completeness` | 是否覆盖了必要要点 |
| `context_relevance` | 检索到的上下文是否切题 |
| `unsupported_claim_rate` | 无依据断言的占比（越低越好） |
| `conflict_disclosure_rate` | 面对冲突来源时是否披露了冲突 |

### 4.15 检索指标（这一节的公式可以直接背）

设 gold（标准答案标注的相关 chunk 集合）大小为 G，检索返回按 rank 排序的列表。

| 指标 | 公式 | 直觉 |
| --- | --- | --- |
| **Recall@k** | 命中的 gold 数 / G | 该找的有多少找回来了 |
| **Precision@k** | 命中的 gold 数 / k | 找回来的有多少是有用的 |
| **MRR@k** | `1 / 第一个相关结果的 rank` | 第一个正确答案排得多靠前 |
| **NDCG@k** | `DCG / IDCG`，其中 `DCG = Σ rel_i / log2(rank+1)` | 带位置折扣的排序质量 |
| **Hit@k** | 是否至少命中 1 个 | 有没有找到 |
| **document_recall@k** | 命中的 gold **文档**数 / gold 文档总数 | 文档级的召回 |
| **gold_chunk_coverage** | 全部检索结果（不限 k）覆盖的 gold chunk 比例 | 整体覆盖情况 |

代码位置：`backend/evaluation/rag.py::_ranking_metrics`。

> MRR 只看第一个命中，NDCG 看整体排序质量。这两个常被混淆，面试常问。
> 注意本项目 `precision_at_10` 会很低（基线报告里是 0.1375）——这是**正常的**：gold chunk 通常只有 1~2 个，分母却是 10。precision 不设门禁。

### 4.16 Provenance（来源凭证）与 Fingerprint（指纹）

**Fingerprint** = 对某个东西做内容哈希，得到一串十六进制字符串。**内容变一个字节，指纹就变**。

**Provenance** = 这份评测结果"从哪来的"标记。本项目只有两个取值：

| provenance | 含义 | 能否代表真实质量 |
| --- | --- | --- |
| `contract_smoke` | 用静态 Observation 文件跑的离线评测 | **不能**。只证明契约/指标/门禁可复现 |
| `live_rag` | 真实调用 RAG、Provider、索引跑出来的 | 能（在受控索引上） |

**两者绝对不能混用**：`gates_v1.json` 只接受 `contract_smoke`，`live_gates_v1.json` 只接受 `live_rag`。

报告的 metadata 里绑定这些指纹（实测输出）：

```json
{
  "adapter": "prediction_file",
  "corpus_id": "orion_controlled_rag_smoke_v1",
  "corpus_fingerprint": "10b8700e...e2bd87",
  "index_id": "controlled-corpus-v1",
  "profile_id": "offline-smoke-v1",
  "profile_fingerprint": "3c28851e...92291",
  "rag_source_fingerprint": "55380e4b...9cf4",
  "provenance": "contract_smoke",
  "source_mismatch_override": false
}
```

**为什么要指纹？** 解决 2.3 表格里的"假对比"痛点：换了模型或索引后拿旧 baseline 比，会得出错误的回归结论。指纹不一致 → **直接拒绝比较**（除非显式 `--allow-source-mismatch`）。

### 4.17 Baseline（基线）与 Regression（回归）

**Baseline** = 上一次"已知良好"的评测结果，存档为 `evals/rag/baseline_v1.json`。

**Regression** = 相对 baseline 变差了。门禁的核心判据就是"**回退幅度是否超过允许值**"。

### 4.18 Gate（门禁）

**一条规则："某个指标必须满足什么条件，否则判失败。"**

见第 10 节。

## 5. RAG 主链路：一条问题怎么走完全程

代码：`backend/rag/pipeline.py`，用 **LangGraph** 组织成状态图。

### 5.1 图结构（来自 `build_rag_graph`）

```
                      classify_complexity   ← 入口
                              │
              ┌───────────────┴───────────────┐
        simple│                               │complex
              ↓                               ↓
       retrieve_initial              prepare_sub_questions
              │                               │
              │                    Send 并发扇出（2~4 个子问题）
              │                               ↓
              │                       rag_sub_agent × N
              │                    （每个子问题：检索 → 评判）
              │                               │
              ↓                               ↓
       grade_documents                    synthesis
              │                               │
   ┌──────────┼──────────┬────────┐           ↓
   ↓          ↓          ↓        ↓          END
rewrite_question  await_hitl   END
   │          │
   ↓          └──(HITL 恢复后重新路由)
retrieve_rewritten
   │
   └──→ grade_documents（只重写一次）
```

**两条路径互不相交**（`pipeline.py:1346-1373`）：

- **simple 路径**：`retrieve_initial → grade_documents →` 按 route 分流。`grade_documents` 的入边**只有** `retrieve_initial` 与 `retrieve_rewritten`。
- **complex 路径**：`rag_sub_agent → synthesis → END`。复杂路径**不经过图上的 `grade_documents` 节点**——子问题的证据评判发生在 `rag_sub_agent` 内部（`pipeline.py:1207` 调用 `grade_documents_node`）。

九个节点：`classify_complexity`、`prepare_sub_questions`、`retrieve_initial`、`grade_documents`、`rewrite_question`、`retrieve_rewritten`、`rag_sub_agent`、`synthesis`、`await_hitl`。

### 5.2 逐步说明

**① 复杂度规划 `classify_complexity`**

- 明显的短单事实问题由**本地规则**直接判为 simple，**不调用模型**（省一次调用延迟）。
- 其余问题由 Fast 角色**一次**完成 simple/complex 判断，complex 时**同时产出最多 `RAG_MAX_SUBQUERIES` 个子问题**——不追加第二次拆题调用。

**② 检索执行**

- simple：`retrieve_initial` 走一次标准检索。
- complex：`Send` API 并发执行子问题的"检索 → 评判"，受 `RAG_MAX_CONCURRENT_SUBQUERIES` 限流。

**③ 证据评判 `grade_documents`**

Grader 一次输出相关性、可回答性、歧义、置信度与 route。路由到：回答 / 一次重写 / HITL 澄清 / 范围选择 / 无知识结束。

**④ 查询重写 `rewrite_question`**（如需要）

Fast 角色一次结构化调用选择 Step-back 或 HyDE。

**⑤ 二次召回 `retrieve_rewritten`**

对重写结果再执行一次检索 + Auto-merging + Rerank + 证据复评。**不会无限重写**。

**⑥ 合成 `synthesis`**（complex 路径）

按 `chunk_id` 去重、合并 RRF 排名、归一化子链路 trace。**单个子问题 Provider 失败只返回结构化失败快照；全部失败才向上抛错**，避免一个子任务拖垮整条链路。

**⑦ 答案生成**

Answer 角色**只使用最终 Evidence** 生成回答。`rag_trace` 记录 route、rewrite method、初次/二次结果、检索模式、降级码、层级、合并信息、RRF score、rerank score 与 Provider issue。

### 5.3 设计亮点（面试可用）

| 亮点 | 说明 |
| --- | --- |
| 一次调用同时完成判定与拆题 | 省掉一次模型往返 |
| 本地规则短路 | 简单问题不付模型延迟 |
| `Send` 并行 + 并发上限 | 复杂问题并行但可控 |
| 单个子问题失败降级 | 子任务失败不拖垮全链路 |
| 只重写一次 | 有界，不会陷入重试风暴 |
| 失败不伪装成无知识 | Provider 失败是 typed error |

## 6. 检索链路深挖：三路召回与融合

### 6.1 一次检索的完整过程

```
目标 target（知识库 / 版本 / 范围）
        │
        ↓ 对 chunk_level == 3（L3）发起 Milvus Hybrid Search
   ┌────┴────┐
   ↓         ↓
Dense      Sparse（原生 BM25）
   └────┬────┘
        ↓ RRFRanker 融合
   候选池（RETRIEVAL_CANDIDATE_K 控制）
        ↓ L3 → L2 → L1 Auto-merging
        │  （父块从版本绑定的 ParentChunk Store 读取）
        ↓ Rerank（可选）
        ↓
   最终 Evidence（带 Document Version / chunk / 内容哈希身份）
```

### 6.2 降级规则（严格且显式）

**只有 `HybridRetrievalUnsupported`（Adapter 明确报告能力不兼容）才允许 Dense fallback**。其他 Provider 失败**显式失败**，不允许静默降级。

Rerank 失败：保留已有融合排序，但必须记录 `rerank_fallback_applied` 标记与原因。

> **仓库级不变式**：Provider 失败不能伪装成"没有知识"；降级必须写进公开 trace，不能静默。

### 6.3 Milvus 侧的过滤安全

Document Version、Tenant、Knowledge Base、chunk level 四个过滤条件在**安全构造的 Milvus filter 中同时生效**，防止跨版本或跨作用域召回。

> 这是多租户场景的关键安全问题：filter 拼接必须参数化/白名单化，不能字符串拼接用户输入。

## 7. 文档入库：Document Version 与三级分块

### 7.1 为什么要有"版本"

一份文档更新了，**旧版本在被新版本替换前必须仍可检索**。否则索引重建期间知识库会短暂"失忆"。

**Document Version 是不可变的**：解析 → 切分 → 嵌入 → 索引 **全部完成后**，才原子发布为当前版本。

### 7.2 七步链路（`README.md` §核心流程 3 + ADR-0015/0016）

1. 前端上传到 `POST /documents/upload/async`；API 保存 source object，并在 PostgreSQL **预留** Document Version 与 Index Job。
2. 索引 worker 用 lease、heartbeat、`SKIP LOCKED`、build fingerprint 与 execution fence 领取 Job。**API 重启不丢任务；旧 fingerprint worker 也不能构建新 profile candidate**。
3. Document Loader 生成带稳定版本身份的**三级分块**；L1/L2 写入 ParentChunk staging，L3 写入**隔离的 Milvus candidate scope**。
4. worker 核验 ParentChunk、Milvus 与 exact manifest，再用 PostgreSQL **CAS**（compare-and-swap）切换 `current_version_id`。
5. **同名旧版本在发布前始终可检索；新版本失败不影响旧版本**（失败 candidate 不污染 current version）。
6. superseded / failed / delete 版本进入持久 cleanup queue，由 worker 用独立 lease 和**数据库时钟退避**执行 exact-version 物理清理。
7. worker crash 后：RUNNING Job 可幂等重建；STAGED Job **只恢复 publish**，不重复解析和向量化。

### 7.3 关键不变式

> **失败 candidate 不污染 current version** —— 这是"原子发布"的核心保证。
> 实现手段：先写到隔离 scope，全部成功后才 CAS 切换指针。

## 9. 评测体系（二）：指标怎么算

### 9.1 打分流程

```
Dataset（期望） + Observation（实际）
        ↓
_score_case：逐 case 对比
   ├── checks：complexity / route / outcome / hitl / hitl_resolution
   │           / hitl_final_outcome / retrieval_hit_at_10 / judge_*
   ├── metrics：recall/precision/mrr/ndcg at k=1,3,5,10
   │            document_recall_at_k / gold_chunk_coverage
   │            rewrite_recall_delta_at_10 / rewrite_improved_at_10
   │            judge 七维 / duration_ms / provider_failed
   └── passed = 所有非 None 的 check 全通过 且 无 provider error
        ↓
_aggregate_metrics：跨 case 聚合（求平均，记录 eligible_cases）
        ↓
_evaluate_gates：与阈值和 baseline 比对
        ↓
Report
```

### 9.2 `k_values = [1, 3, 5, 10]`

每个排序指标都算 4 个 k，所以报告里有 `recall_at_1`、`recall_at_3`、`recall_at_5`、`recall_at_10` 等。

### 9.3 聚合的两条重要规则

**规则一：`eligible_cases`（合格 case 数）**

每个聚合指标都记录"有多少 case 真正参与了这个指标的计算"。看起来是细节，但它防的是一个隐蔽作弊：**通过减少有效样本让指标好看**。

门禁里专门有这条检查（`_evaluate_metric_gate`）：

```python
elif (current.eligible_cases < baseline.eligible_cases and gate.required):
    failures.append(f"eligible case count dropped from "
                    f"{baseline.eligible_cases} to {current.eligible_cases}")
```

**规则二：`gold_chunk_coverage` 是加权平均，不是简单平均**

```python
gold_total = sum(case.gold_chunk_count for case in cases)
matched_total = sum(case.matched_gold_chunk_count for case in cases)
aggregated["gold_chunk_coverage"] = matched_total / gold_total
```

即：gold chunk 多的 case 权重更大。这符合直觉——大 case 的覆盖情况更值得关注。

> **这是很好的工程习惯示范**：指标拿不到数据时，报告写清"为什么拿不到、缺什么能力"，而不是留空让人误以为"通过了"。

### 9.5 Tag Slices（按标签分组）

报告会按 tag 分组统计 case_pass_rate 和 outcome_accuracy，这样能看出**哪类问题变差了**：

```
| Tag              | Cases | Case pass rate | Outcome accuracy |
| `multi_hop`      | 2     | 1              | 1                |
| `no_knowledge`   | 2     | 1              | 1                |
| `source_conflict`| 1     | 1              | 1                |
```

2.4 节的场景（rerank 阈值调高导致多跳变差）就是靠这个切片定位的。

## 10. 评测体系（三）：门禁与 CI 卡口

### 10.1 门禁 = 一条规则

```json
{
  "metric": "document_recall_at_10",
  "direction": "higher_is_better",
  "minimum": 0.95,
  "max_regression": 0.02,
  "required": true
}
```

四条规则**同时生效**，违反任意一条 → FAILED：

| 条件 | 代码 | 含义 |
| --- | --- | --- |
| 绝对线 | `if actual < gate.minimum` | 必须 ≥ 95% |
| 相对线 | `if actual < baseline - max_regression` | 比 baseline 最多掉 2% |
| 必需性 | `if actual is None: FAILED if required` | 拿不到数据 = 失败 |
| 样本量 | `if current.eligible_cases < baseline.eligible_cases` | 不许靠减少样本美化 |

代码：`backend/evaluation/rag.py::_evaluate_metric_gate`（第 1215 行）。

### 10.2 两类全局门禁（一票否决）

| 门禁 | 作用 |
| --- | --- |
| `required_provenance` | 报告来源必须匹配（`gates_v1.json` 要求 `contract_smoke`）。防止离线假数据和实跑数据混着比 |
| `critical_no_regression` | **关键用例零回退**，一条都不许挂 |

### 10.3 两套门禁的差异（完整 14 条）

| 指标 | offline minimum | live minimum | offline max_regression | live max_regression |
| --- | ---: | ---: | ---: | ---: |
| `case_pass_rate` | **1.0** | 0.95 | 0 | 0 |
| `complexity_accuracy` | 1.0 | 0.9 | 0.01 | 0.02 |
| `document_recall_at_10` | 0.95 | 0.9 | 0.02 | 0.02 |
| `gold_chunk_coverage` | 0.95 | 0.9 | 0.02 | 0.02 |
| `hitl_accuracy` | 1.0 | 0.9 | 0.01 | 0.02 |
| `hitl_final_outcome_accuracy` | 1.0 | 0.9 | 0 | 0.02 |
| `hitl_resolution_success_rate` | 1.0 | 0.9 | 0 | 0.02 |
| `mrr_at_10` | 0.95 | 0.8 | 0.02 | 0.02 |

| `outcome_accuracy` | 1.0 | 0.9 | 0.01 | 0.02 |

### 10.4 CI 卡口：`.github/workflows/rag-eval.yml`


**关键点逐个解释：**

- **⑤ `--check`**：生成的 schema 必须和代码一致。有人手改生成物绕过检查 → CI 挂。
- **⑥ `cmp`**：重算的 baseline 必须和提交的版本**逐字节相同**。这保证 baseline 不是手工编的，而是能从 Dataset + Observation 确定性重建的。
- **⑦ base 分支 baseline**：这才是"回归"的正确语义——**和 PR 目标分支的 baseline 比**，而不是和 PR 自己的比。
- **⑧ `--fail-on-regression`**：这就是开关。没有它 → 只出报告（退出码 0）；有它 → 门禁 FAILED 时退出码 1 → step 失败 → job 失败 → **PR 显示红叉**。配好 branch protection 后直接禁止合并。
- **⑨ `if: always()`**：即使失败也上传报告。失败时必须能立刻看到证据，而不是"CI 挂了你去查吧"。
- **`--allow-source-mismatch`**：base 分支的 baseline 与 PR 的 `rag_source_fingerprint` 必然不同（代码改了），所以这里显式放行。这是**有意的、可见的**例外，不是静默豁免。

## 11. 评测体系（四）：持久化 Job 的租约与 fencing

这是整个项目**工程最硬**的部分，也是面试最容易被追问的地方。

### 11.1 问题：多个 worker 抢一个 Job 会怎样

假设两个 worker 同时处理同一个评测 Job：

- 都写结果 → 结果错乱 / 重复计费
- worker A 卡死但没退出，worker B 接手；A 后来"醒了"继续写 → **覆盖 B 的正确结果**

这叫**脑裂（split-brain）**。纯靠"检查进程是否活着"解决不了。

### 11.2 解决办法：Lease + Heartbeat + Fencing Token

| 机制 | 作用 |
| --- | --- |
| **Lease（租约）** | worker 领取 Job 时获得一段时间的"所有权"，写入 `lease_expires_at` |
| **Heartbeat（心跳）** | worker 定期续租。**停跳 → 租约过期 → 别人可接手** |
| **Fencing Token（栅栏令牌）** | 每次领取 `fencing_token += 1`。写入时必须带上自己的 token，**不匹配就拒绝** |
| **`FOR UPDATE SKIP LOCKED`** | 数据库级并发领取：锁住的行被别人跳过，避免两个 worker 领同一个 Job |

**Fencing 的精髓**：过了期的 worker 即使还活着，它的 token 已经旧了，**写不进去**。

### 11.3 代码对应（`backend/evaluation/repository.py`）

```python
def claim_next(self, worker_id, lease_seconds):
    ...
    .with_for_update(skip_locked=True)
    ...
    job.lease_expires_at = now + timedelta(seconds=max(10, lease_seconds))
    job.fencing_token += 1          # ← 每次领取递增
```

```python
def heartbeat(self, worker_id, fencing_token, lease_seconds):
    ...
    self._assert_owner(job, worker_id, fencing_token)   # ← 所有权校验
    job.lease_expires_at = ...
```

所有写操作都过这一关：`heartbeat`、`claim_case`、`complete_case`、`fail_job`、`finish_job`。

### 11.4 故障收敛：`reconcile_expired`

```python
def reconcile_expired(self, *, now=None):
    """把租约过期的 RUNNING / CANCELLING Job 收敛掉"""
    jobs = (db.query(RagEvaluationJobRow)
        .filter(
            RagEvaluationJobRow.status.in_((RUNNING, CANCELLING)),
            RagEvaluationJobRow.lease_expires_at.is_not(None),
            RagEvaluationJobRow.lease_expires_at <= current,
        )
        .with_for_update()
        .all())
    for job in jobs:
        if job.status == CANCELLING:
            self._cancel_locked(db, job)          # 取消意图优先
            continue
        if job.attempts >= job.max_attempts:
            # 超过最大重试 → 生成 partial report 落库（保留已完成 case 的审计）
            report = self._orphaned_partial_report(job=job, dataset=..., cases=...)
        ...
```

**关键设计**：

- 超过 `max_attempts` **不是简单丢弃**，而是产出 **partial report**（`stage: "lease_recovery"`），保留已完成 Case 的审计记录。
- CANCELLING 状态**优先于重试**——用户的取消意图不能被重试覆盖。

### 11.5 Case 级也有独立 claim

不只 Job 级，**每个 Case 也单独 claim / complete**。这保证长任务被打断后，已完成的 Case 结果不丢、不重算。

### 11.6 面试三问（`prj-pre/backend-agent-project-resume-pack.md` 里的"必答三问"）

| 问题 | 答法 |
| --- | --- |
| 为什么说评测结果可信？ | 版本化契约 + 指纹 + provenance + 门禁；LLM 不当唯一判官，核心指标由确定性代码计算 |
| 过期 worker 怎么防？ | lease + `fencing_token` + 单事务 ownership 校验（`_assert_owner`） |

## 12. 可恢复运行：Thread / Run / Event / HITL

### 12.1 为什么要"可恢复"

用户刷新页面、网络断开、SSE 断了 —— 这些**都不应该影响正在执行的 Agent**。

### 12.2 九步全链路

1. 客户端 `POST /v1/threads` 获取服务端生成的 `thread_<uuid>`。
2. 客户端 `POST /v1/threads/{thread_id}/runs`，提交 message、`idempotency_key`、期望 Thread version、并发策略、断连策略、可选 `approved_tools`。
3. Run Service **在同一事务中**追加用户 Message、assistant placeholder、Run 和初始 Event，返回 durable `run_id` 与新的 `thread_version`。
4. `RunAgentExecutor` 用 owner lease 与 fencing token 领取执行，通过 `AgentRuntimeFactory` 构建固定中间件链和**冻结的 Model Snapshot**。
5. Agent 根据 Skill 决定是否调用知识库、天气、Web、SQL、Sandbox 等 Tool。
6. Tool progress、检索状态、Message delta、HITL 和 terminal 结果**先进入 PostgreSQL Event Journal**。
7. 客户端通过 `GET /v1/runs/{run_id}/stream` 观察 SSE；断线后用 `Last-Event-ID` 重连，或 `/events?after={sequence}` 补放。
8. `message.completed` 是最终正文与 `rag_trace` 的**权威来源**；assistant Message 与 Run 终态提交后才发布 `run.completed` / `run.failed` / `run.cancelled`。
9. `hitl.required` 将 Run 置为 `waiting_input`；Stop 调用 `/cancel` 并**继续监听**权威 terminal Event。

### 12.3 HITL 的幂等恢复

- 歧义问题 → LangGraph 原生 `interrupt` 挂起
- Run 落到 `waiting_input`，**持久化 checkpoint**
- 用户提交一次性 `hitl_token` + 幂等键 → 从**同一节点**恢复
- token 消费走**单事务** `consume_resume`
- 重复提交 → 命中幂等，返回**同一 checkpoint**（不重复触发、不越权恢复）

### 12.4 核心不变式（来自 CLAUDE/AGENTS 的仓库级约束）

> - 一个 Run 绑定用户、Tenant、Thread、幂等键、一个用户 Message 和一个 assistant Message。
> - HITL 必须恢复同一 Run、同一 Checkpoint 和同一 assistant Message；**不能重新提问来模拟恢复**。
> - 终态只能由持久事务写入 `message.completed` 与权威 terminal Event；**关闭 SSE 或浏览器不等于取消 Run**。
> - Run-local Queue、loop、trace、budget、Evidence、Model Snapshot 和 capability 必须由**显式 request context** 持有。**禁止模块级"当前请求""最后一次 trace"或共享可变 Queue**。

最后那条是**跨 Run 状态泄漏**防护：两个并发 Run 绝不能共用可变全局状态。回归测试要求"两个并发 Run 的隔离测试"。

## 17. 事实边界与常见误解

### 17.1 必须诚实标注的边界

| 事实 | 说明 |
| --- | --- |
| **SuperMew 不是你写的** | 它是 MIT 开源项目，你的仓库是 fork。简历必须写"基于/复现并改造"，不能写"我实现了" |
| **P0–P3 不产出新功能** | 本质是"跑通 + 理解 + 留证据"，产出物是面试防御材料 |
| **真正属于你的只有 P4** | FR-9 失败归因 + FR-10 Holdout 对比 |
| **offline smoke 不代表生产质量** | `contract_smoke` provenance 只证明契约/指标/门禁可复现 |
| **`prompt_injection` case 只验证检索** | 带 `retrieval_only` 标签，不能据此宣称完整 Guardrail 通过 |
| **LLM 评分不是唯一判据** | 核心指标由确定性代码计算 |
| **多智能体只是"并行子问题 + Grader 路由"** | 不是 planner/researcher/writer 角色协作；那是规划中的改造点 |
| **当前 Dataset 只有 20 条** | 生产门禁目标 ≥ 200 条 |
| **报告里多个指标是 N/A** | 因为离线 Observation 没有 judge 数据，报告明确写明了原因 |

### 17.2 常见误解纠正

| 误解 | 纠正 |
| --- | --- |
| "SSE 断了就是 Run 取消了" | 不是。终态只能由持久事务写入；SSE 只是投影 |
| "用户点了停止，前端可以立刻标 cancelled" | 不可以。要等 `message.completed` 和权威 terminal Event |
| "Provider 挂了就当没查到" | 不允许。Provider 失败是 typed error，不能伪装成 `NO_KNOWLEDGE` |
| "Hybrid 效果不好就自动退回 Dense" | 只有 Adapter 明确报告能力不兼容（`HybridRetrievalUnsupported`）才允许 |
| "Rerank 挂了就让整条链路失败" | 不必要。保留融合排序 + 记录降级标记 |
| "改了模型配置，正在跑的任务应该跟着变" | 不应该。Model Snapshot 在创建时冻结 |
| "评测 Job 就是一个 Run" | 不是。Run 产生面向用户的 Thread Message；Evaluation Job 产生 Case Observation 与脱敏 Report |
| "改了 Dataset 可以直接复用旧 Observation" | 不行。fingerprint 变化 → 旧 Observation 被拒 |
| "precision_at_10 只有 0.1375，肯定有 bug" | 正常。gold chunk 通常 1~2 个，分母是 10；precision 不设门禁 |
| "CI 挂了你自己去查吧" | 反面。报告作为 artifact 上传，PR 里直接可看 |

## 附：一句话总结

**SuperMew 是一个把"RAG 质量"变成"可回归、可审计、可拦截"的工程系统的 Agent 平台。**
它的核心不是"让模型答得更好"，而是**让"是否变得更好"这件事本身可信**——通过版本化契约、内容指纹、确定性指标、发布门禁与 CI 卡口，把调参从人肉试错变成可证明的工程流程。

RagProof 是基于它的二次开发项目，自研增量落在失败归因与 Holdout 对比，落点全部在"自研区"（`backend/evaluation/reporting/`、`scripts/`、`tests/`），不触碰上游核心状态模型。
